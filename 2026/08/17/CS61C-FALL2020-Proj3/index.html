CS61C_FALL2020_Proj3

记录通过CS61C的2020年秋季学期proj3的整个项目。

参考Project3 | CS自学社区

该项目让我们使用logisim来做了一个二级流水线CPU。如图所示，能够通过所有测试，以及要求中RISC-V的指令。（贴在后面）

本文为了防止抄袭之类的，仅仅展示CPU界面以及通过测试的输出，但会说明逻辑控制的一些问题。（不过你可以下载我的CS61C学习仓库来进行查看学习，但请遵守CS61C课程的基本原则，不要抄袭。）

CPU

Control Logic Design

逻辑控制是项目里比较难的部分：控制单元以指令中的 opcode、funct3、funct7 三组位段作为输入（正好对应 3 个输入信号），解析出 11 个控制信号去驱动数据通路。

其中最关键的是 ALUSel：它直接控制 ALU 运算类型的选择。由于几乎所有指令都要经过 ALU——R 型 / I 型要算数运算，访存指令要用 ALU 计算地址，分支指令要用 ALU 做比较——我们必须对 funct3、opcode 甚至 funct7 一起解析，才能确定每条指令该选哪一种 ALU 运算。比如当 opcode 为 0x63（B 型分支指令）时，ALUSel 必须选为 0，让 ALU 完成 rs1 与 rs2 的比较，否则分支跳转指令都会解析失败、产生错误结果。

对每一个控制信号，都要逐一考虑：哪些指令会用到它、它在这些指令下应该取什么值。

Pipeline Hazard Handling

本设计是二级流水线：IF（取指）一个阶段，译码 + 执行 + 访存 + 写回合并在 EX 一个阶段，两个阶段之间用流水线寄存器 inst_ID 传递指令。以及一个 PC_ID 来存储指令

  • 数据冒险：寄存器堆的写回发生在 EX 阶段末尾，而下一条指令的寄存器读取发生在下一周期 EX 阶段开头，写后读（RAW）依赖天然被流水级错开，因此不需要数据转发，也不需要停顿。
  • 控制冒险：分支 / 跳转指令要到 EX 阶段才能解析出目标地址（或是否跳转），此时下一条指令已经被取进 inst_ID 寄存器了。处理方法是：检测到跳转（含分支跳转）时，把 inst_ID 寄存器里的指令替换成 NOP（0x00000013），让这条已取出的延迟槽指令作废，CPU 再从正确的目标地址继续执行。

0x00000013 正是 RISC-V 的规范 NOP 编码：addi x0, x0, 0——对 x0 写 0，没有副作用，不会触发寄存器堆写使能或访存，所以用作”冲刷”指令非常安全。

RISC-V 指令实现（含 CSR）

官方测试覆盖了以下几类指令：

  • 算术 / 逻辑：addi、add、lui、sll 等
  • 访存：load / store（cpu-mem test）
  • 分支跳转：branch、jump、branch-jump
  • 系统类（CSR）：csrw、csrwi

其中 CSR 指令值得单独说明：csrw 是 csrrw x0, csr, rs1 的伪指令，把 rs1 的值写入 CSR 寄存器（目标寄存器是 x0，读出的旧值直接丢弃）；csrwi 是 csrrwi x0, csr, imm，立即数版本。CSR 指令的 opcode 为 0x73，通过 funct3 区分读写类型（csrrw 为 001，csrrwi 为 101）。官方给的CSR实现方法很简单，算是一个模拟，没有真正的CSR寄存器组。

Contact to CS61C

解析完指令后，就会明白 RISC-V 的立即数为什么故意拆分得特别散。

RISC-V 不像 x86 那样把立即数连续拼在指令尾部，而是把不同指令类型的立即数位段”打散”在指令字中：

  • I 型（addi / lw / jalr 等）：inst[31:20]，12 位，符号扩展
  • S 型（sw 等）：inst[31:25] | inst[11:7]，12 位，符号扩展
  • B 型（分支）：inst[31] | inst[7] | inst[30:25] | inst[11:8]，13 位（含符号位与最低位 0，2 字节对齐）
  • U 型（lui / auipc）：inst[31:12]，20 位，低 12 位补 0
  • J 型（jal）：inst[31] | inst[19:12] | inst[20] | inst[30:21]，21 位（2 字节对齐）

这样设计是为了硬件复用：B 型复用了 S 型的位段位置（只是把符号位和最低位换了个位置），J 型复用了 U 型的高 20 位位置，这样译码阶段只需少量多路选择器（MUX）就能从同一组线上重组立即数，节省大量布线和逻辑；同时所有指令的寄存器号（rd / rs1 / rs2）都固定在 inst[11:7]、inst[19:15]、inst[24:20]，寄存器堆译码完全不用动。

所以在实现时，需要根据指令类型（ImmSel）把对应位段重新拼接，再做符号扩展（Sign Extension），才能送进 ALU 或地址计算单元——这就是”立即数为什么拆得散”的答案。
