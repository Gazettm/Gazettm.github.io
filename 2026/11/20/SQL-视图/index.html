SQL:视图

Author: Gazettm Date: 十一月 20, 2026  18:27:59 Category: SQL

视图

假设我们在做一个班级名单页面。学生表有姓名、班级和邮箱，页面只需要一班学生的编号和姓名。可以把这条查询保存成一个视图，以后直接查视图，页面就不用每次都写一遍筛选条件。

MySQL 的普通视图保存的是查询定义。读视图时，MySQL 根据这份定义去读原表，因此原表中的结果变了，视图查出来的结果也会跟着变。

WITH CHECK OPTION

这里有一个问题。如果一个视图只显示id >= 10的学生，我们通过视图插入id = 8，MySQL 会不会接受？

对可更新视图，可以用WITH CHECK OPTION来检查INSERT的新行和UPDATE修改后的行。比如设置了id >= 10的检查，写入后id = 8就会报错。多层视图中，还要看检查会走到哪一层。

第二条成功。查询student得到了下面这一行，查询v_local则是空结果。

为什么插进去了却看不到？v1的id <= 20一直参与查询。通过v_local写入时，MySQL 检查了这一层的id >= 10，而v1没开启检查选项，所以25可以写入。v_cascaded会把检查传到v1，即使v1的定义没写检查选项，25也会被挡住。

  • LOCAL检查当前视图。沿着依赖继续往下时，各层按自己的检查选项处理。
  • CASCADED检查当前视图，并把检查传到所有下层视图。只写WITH CHECK OPTION时，默认就是CASCADED。

外层视图没写CHECK OPTION

哪些视图不能更新

前面的名单能更新，因为改一行名单，可以找到它对应的学生。我们再看一个统计每班人数的视图。

这里的2来自两条学生记录的计数。直接改成3，MySQL 没有一条对应的原表记录可改。要让一班多一人，应该在学生表里增加一条一班的记录。

使用聚合函数、窗口函数、DISTINCT、GROUP BY、HAVING、UNION或UNION ALL的视图都不可更新。已经建好的视图可以到INFORMATION_SCHEMA.VIEWS里看。

什么时候用视图

  1. 省掉重复的查询。 比如班级名单的筛选和列名统一写进视图，页面有额外条件时，再在视图外面加WHERE。
  2. 限制调用方能看到的数据。 给名单账号授予视图的SELECT权限，让有权限的定义者访问原表（SQL SECURITY DEFINER），并确保名单账号没有直接读原表的权限，它就只能读到名单视图提供的行和列。MySQL 也支持对原表按列授权。需要同时限制行范围时，可以把筛选条件写在视图里。
  3. 让查询方继续使用同一组列名。 假设原表以后把name改叫full_name，维护者可以更新名单视图的定义，仍然对外提供student_name。用视图的页面就可以继续用原来的查询。
