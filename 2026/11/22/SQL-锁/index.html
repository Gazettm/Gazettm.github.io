MySQL的锁

前面做UPDATE优化时有一个现象。连接 A 只改了一行，连接 B 更新另一行，有时也会等。要知道 B 在等什么，我们得先看锁加在了哪里。

这篇用预约表做几个对照。全局锁看整个 MySQL 实例，表级锁看一张表或它的定义，InnoDB 的行级锁还要往下看具体的索引记录和间隙。下面的输出来自 MySQL 8.0.46。

先在单独的练习实例里建表。后面用 A、B 两个连接操作，C 用来看锁。三个连接都执行USE lock_demo;。

为了让等待的结果更容易看，把 B 的超时调成一秒。lock_wait_timeout用于这里的元数据锁等待，innodb_lock_wait_timeout用于这里的 InnoDB 行锁等待。后面观察等待中的ALTER TABLE时，会临时给它多留几秒。

全局锁

加一把全局读锁

如果备份先读订单表，过一会儿才读订单明细表，中途有事务更新了这两张表，备份就可能把两个时间点的数据拼在一起。用FLUSH TABLES WITH READ LOCK取得全局读锁后，普通查询仍能进行，其他连接对普通表的写入、改表以及已有写事务的提交会受到阻塞。

先在同一个实验实例里建一个独立的库，方便确认锁的范围。

A 保持连接。B 先读当前库，再去写另一个库。下面的语句可以逐条执行，后两条各会等待约一秒。

备份时怎么选

如果备份需要在导出期间阻止写入，可以让mysqldump用--lock-all-tables取得全局读锁。它的范围还是整个实例。对于本例这种全是 InnoDB 的库，可以用一致性快照导出，普通写入可以继续。

我另外在 A 把id = 20的note改成editing、保持未提交时执行了快照导出。备份成功，导出里这行的note仍然是已提交的b。--single-transaction给的是事务表的一致视图，MyISAM 等非事务表没有这个快照。导出过程中还要避开对导出表的ALTER TABLE、DROP TABLE和TRUNCATE TABLE等结构操作。

小结

全局读锁影响同一实例里的各个库。上面的lock_other虽然和正在读的预约表不在一个库，写入仍然被挡住。只备份 InnoDB 表时，可以用事务快照保留一致性，让普通写入继续。

元数据锁（MDL）

表结构也要有锁保护。我们让 A 开一个事务，执行普通SELECT，看 B 能不能改这张表的结构。

趁 B 还在等，用 C 查performance_schema.metadata_locks。

A 的查询已经返回了b，但事务还没结束，SHARED_READ仍然在。B 的ALTER TABLE已经拿到SHARED_UPGRADABLE，还在等EXCLUSIVE。A 在八秒内执行COMMIT;后，B 就能完成改表。我随后查列信息，发现marker已经加上了。试完把 B 的lock_wait_timeout改回 1。

普通SELECT会持有SHARED_READ，INSERT、UPDATE和DELETE等写操作通常拿SHARED_WRITE。这两种常见的 MDL 可以共存。改表需要的排他 MDL 会和它们冲突。所以应用即使只开了一个读事务，查完不提交，也会拖住下一次改表。

意向锁

假设 A 已经锁了某条记录，B 又想给整张表加锁。InnoDB 会先在表上记录一个意向，B 看表级的锁信息就能判断有没有冲突，无需把每行的锁都检查一遍。

小结

显式表锁用LOCK TABLES申请，会限制对整张表的读写。MDL 由 MySQL 自动加上，保护事务使用的表定义。意向锁是 InnoDB 用来协调表锁与行锁的。同一次操作可以同时留下 MDL、意向锁和记录锁。

行级锁

InnoDB 的表数据按索引组织，所以加行锁时要看实际走了什么索引。下面查锁都用 C 执行这条语句。

下面先用REPEATABLE READ（RR）。要复现的话，在 A、B 各自执行SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;，再开始事务。每组结束后用ROLLBACK释放行锁并恢复本组的数据。

SELECT ... FOR SHARE可以用旧写法LOCK IN SHARE MODE。SELECT ... FOR UPDATE获取排他锁，INSERT、UPDATE、DELETE会自动对各自修改的记录加排他锁。RR 和READ COMMITTED（RC）里的普通SELECT通常走一致性读，不请求行锁，表定义仍由 MDL 保护。

间隙锁：等值查询没有命中

主键里有 20 和 30，没有 25。A 对id = 25执行加锁查询。

查询是空的。C 看到的记录类型锁却有一条PRIMARY X,GAP 30。这里的 30 是间隙右边的那条索引记录，锁定的是开区间(20, 30)。

B 查 26 也返回空结果。C 在两边都查完时看到两条X,GAP 30，同一段间隙可以同时被两边锁住。但 B 接着插入 25 会报ERROR 1205，因为插入被 A 的间隙锁挡住。结束时 A 也回滚。

把 A 改成 RC 再做一遍。

这次只看到TABLE IX。B 开启新事务，执行刚才失败的插入语句，ROW_COUNT()返回 1。B 回滚这次插入，A 也回滚。RC 下，普通搜索和索引扫描通常不加间隙锁，检查外键和重复键时仍可能用到。

没有合适的索引

最后换成没有索引的note做更新条件。

语句只改了主键 20，但在 RR 下，它扫描了聚集索引。C 查到四条主键记录全带X，还有索引末端的supremum pseudo-record和表级的IX。B 执行UPDATE booking SET note = 'other' WHERE id = 40;也等到超时。A 最后回滚。

看上去像锁了整张表，但data_locks里表级的锁仍然是IX，挡住 B 的是扫描期间取得的索引锁。排查这类更新时，先看执行计划实际扫了哪些记录，再看事务什么时候结束。

小结

主键等值命中已有记录时，本例只锁那条记录。主键等值未命中时，RR 可以锁住值本来应该插入的间隙。范围查询和普通索引等值查询还会出现临键锁，锁住索引记录和它前面的间隙。能否插入要看新键落在哪段区间，能否更新则要看已有记录本身有没有被锁。
