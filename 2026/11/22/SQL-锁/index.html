MySQL的锁

前面做UPDATE优化时有一个现象。连接 A 只改了一行，连接 B 更新另一行，有时也会等。要知道 B 在等什么，我们得先看锁加在了哪里。

这篇用预约表做几个对照。全局锁看整个 MySQL 实例，表级锁看一张表或它的定义，InnoDB 的行级锁还要往下看具体的索引记录和间隙。下面的输出来自 MySQL 8.0.46。

先在单独的练习实例里建表。后面用 A、B 两个连接操作，C 用来看锁。三个连接都执行USE lock_demo;。

为了让等待的结果更容易看，把 B 的超时调成一秒。lock_wait_timeout用于这里的元数据锁等待，innodb_lock_wait_timeout用于这里的 InnoDB 行锁等待。后面观察等待中的ALTER TABLE时，会临时给它多留几秒。

全局锁

加一把全局读锁

如果备份先读订单表，过一会儿才读订单明细表，中途有事务更新了这两张表，备份就可能把两个时间点的数据拼在一起。用FLUSH TABLES WITH READ LOCK取得全局读锁后，普通查询仍能进行，其他连接对普通表的写入、改表以及已有写事务的提交会受到阻塞。

先在同一个实验实例里建一个独立的库，方便确认锁的范围。

A 保持连接。B 先读当前库，再去写另一个库。下面的语句可以逐条执行，后两条各会等待约一秒。

小结

全局读锁影响同一实例里的各个库。上面的lock_other虽然和正在读的预约表不在一个库，写入仍然被挡住。只备份 InnoDB 表时，可以用事务快照保留一致性，让普通写入继续。

元数据锁（MDL）

先用预约表区分一下数据和元数据。id = 20这行的note是b，这个b是数据。note叫这个名字、类型是VARCHAR(32)、不允许存NULL，这些是表的定义，也就是元数据。把这一行的note改成editing是在改数据。用ALTER TABLE增加一列是在改表的定义。

元数据锁（Metadata Lock，MDL）保护的是表的定义。 MySQL 在访问表时会自动申请它。假设 A 的事务已经用了booking，B 此时想删掉note列，MySQL 会先让 B 等，直到 A 用完目前的表定义。下面用添加一列复现这个等待。

普通SELECT为什么会挡住ALTER TABLE

第一步。 A 开事务，查一条记录。先记下连接编号，等会儿用它来认锁表里的行。

查询返回了b。先停在这里，保留事务。SELECT执行完和事务结束是两件事。这里显式开启了事务，表上的 MDL 要等到COMMIT或ROLLBACK才释放。

第二步。 B 也查自己的连接编号，再试着给表加一列。把等待时间临时设长一点，留够时间切换窗口。

B 的ALTER TABLE停在这里。趁它还在等，切到 C 执行第三步。

第三步。 C 查元数据锁。metadata_locks用OWNER_THREAD_ID标识持有或申请这把锁的线程。连上threads表，可以换成刚才CONNECTION_ID()查出的连接编号。

我这次跑出来的 A 是 8，B 是 9。你看到的编号会随连接变化。

  • A 的SHARED_READ已经拿到了。 GRANTED表示锁已授予，TRANSACTION表示按事务释放。A 虽然已经查出了结果，事务仍在使用这张表。
  • B 已拿到可升级的锁，还在等排他锁。 SHARED_UPGRADABLE是它为改表先取得的 MDL。真正变更表定义时还需要EXCLUSIVE，这把锁与 A 持有的SHARED_READ冲突，所以状态是PENDING。

我同时到performance_schema.data_locks查了同一张表，得到 0 条 InnoDB 数据锁。这就能看出问题出在哪一层了。A 只做了普通查询，仍然能靠它持有的 MDL 挡住 B 改表。

第四步。 回到 A 执行COMMIT;。B 会接着完成改表。回到 B 确认新列，并恢复超时设置。

SHOW COLUMNS实际返回了marker，类型为int，允许为NULL。如果等到 B 自己报了ERROR 1205才提交 A，B 需要重新执行ALTER TABLE。

再想一个常见的情况。假如 A 开着自动提交，直接执行这条SELECT，查询结束也就是这次事务结束。我重新按这种方式查了一次，返回b后让 C 再查同一张表，已经看不到这条 MDL。平时碰到改表一直等，可以先找有没有查完数据却还没结束的事务。

意向锁

现在把问题换一下。A 要改预约编号 20，B 要改编号 30。两个人想锁的是不同的记录，可以各改各的。如果此时又有一个事务想给整张表加锁，InnoDB 怎么知道表里已经有人在锁记录？

InnoDB 在申请记录上的锁之前，会先在表上放一把意向锁。这让整表锁的申请者先在表这一层判断冲突，省去逐个检查记录的工作。

这里先认识两个缩写。S是共享锁，多个事务可以在同一条记录上同时持有。X是排他锁，拿到它以后，其他事务就要等这把锁释放，才能在这条记录上取得S或X。加上表示意向的I，就是下面这两种表级锁。

InnoDB在表上加的锁 事务接下来要在记录上申请 另一事务申请整表S 另一事务申请整表X
IS，意向共享锁 S 兼容 冲突
IX，意向排他锁 X 冲突 冲突

IX的含义是这个事务要对表里的记录加排他锁，两把IX本身可以共存。编号 20 和 30 的例子里，A 和 B 都会有IX。它们在下一层分别锁自己的记录，所以能同时改。下面会在锁表里看到这些记录。

小结

LOCK TABLES是手动限制整张表的读写。MDL 保护正在使用的表定义，查完还没提交也可能挡住改表。意向锁则是 InnoDB 给行锁留下的表级信息。普通UPDATE就能同时用到 MDL、表级IX和具体的记录锁。

行级锁

先看这张表的主键索引。四条记录按编号排开。

InnoDB 在索引上加锁。它可以锁一个已有的键，例如 20，也可以锁两个键之间的位置，例如 20 和 30 之间。锁已有记录会影响其他事务对这条记录加锁，锁住间隙会限制往这段位置插入新键。

接下来 A、B 先用可重复读（REPEATABLE READ，简称 RR）。两个连接各执行一次下面的设置，后续新开的事务就使用这个隔离级别。

输出列 怎么读
LOCK_TYPE TABLE是表级锁，例如IS和IX。RECORD表示用索引记录来描述锁，间隙锁也列在这一类里

记录锁：两个人锁同一条记录

先用主键等值查找id = 20。这是已经存在的一条记录，给它加一把共享锁。

A 返回 20。此时用 C 查锁。

两行分别对应表和记录。首先是表上的IS，表示 A 要在记录上取共享锁。然后是主键 20 的S,REC_NOT_GAP。REC_NOT_GAP表示锁的范围到这一条记录为止，前面的间隙没有被这把锁覆盖。

A 先不回滚，让 B 也查 20，再尝试改同一行。

B 的FOR SHARE也返回 20，因为两把共享锁兼容。B 接着更新时需要对 20 取得排他锁，A 的共享锁还在，所以写入等到报ERROR 1205。B 回滚之后，A 也执行ROLLBACK;。

趁 B 的事务也还开着，让 C 再查一次。现在能看到两条TABLE IX，还有两条X,REC_NOT_GAP，分别落在主键 20 和 30 上。这就是前面说的意向锁兼容。最后在 B 和 A 分别执行ROLLBACK;。

在 RR 和读已提交（READ COMMITTED，简称 RC）下，普通SELECT通常是一致性读，也就是按当前读视图选可见的版本。FOR SHARE和FOR UPDATE则是加锁读，分别申请共享锁和排他锁。FOR SHARE也可以写成旧语法LOCK IN SHARE MODE。INSERT、UPDATE、DELETE会对它们修改的记录加排他锁。

间隙锁：查不到记录，为什么插入还会等

主键索引里有 20 和 30，没有 25。假设 A 按id = 25做加锁读，这时查不到现成的记录。要防止另一个事务在 A 结束前插入 25，InnoDB 可以把 25 将来会进入的位置锁住。本例中，这个位置落在(20, 30)，也就是大于 20、小于 30 的那段间隙。

A 返回空结果。让 C 查锁，其中一行是RECORD PRIMARY X,GAP 30。GAP说明这把锁保护的是间隙，30是这段间隙右边的索引记录，所以输出显示 30，实际保护的是 20 和 30 之间的位置。

接着让 B 在同一个间隙里查一个不存在的编号。

B 也立即返回空结果。此时 C 能看到两条X,GAP 30。这里虽然两条都带X，它们都是纯间隙锁，可以同时保护同一段间隙。接下来才是会产生等待的操作。

插入需要在间隙里放入新键，因此被 A 的间隙锁挡住，B 报ERROR 1205。A 也执行ROLLBACK;后，这一轮结束。

换成读已提交后再插入

把 A 切到 RC，其他条件沿用刚才的例子。先由 A 查 25，再由 B 插入 25。这一轮 B 不需要再执行查 26 的语句，直接验证 A 还会不会挡住插入。

C 这次只查到TABLE IX，没有主键索引上的X,GAP。

B 的ROW_COUNT()返回 1，插入成功。两边都回滚。这个对照里，RR 锁住了未命中的键所在的间隙，RC 的同一条加锁查询没有锁这段间隙。RC 的普通索引搜索和扫描一般不加间隙锁，外键检查和重复键检查仍可能用到。

临键锁：已有的键和它前面的间隙一起锁

临键锁（next-key lock）是一把记录锁加上该记录前面的间隙锁。 比如锁住主键 20 的临键锁，范围就是(10, 20]，从 10 之后开始，包含键 20。其他事务既不能在 10 和 20 之间插入，也不能拿到 20 上与当前锁冲突的锁。

把 A 切回 RR。这次用范围条件做加锁读，留意左边查到的记录和右边的停止位置。

小结

按主键等值查已存在的行，先看记录锁。查不到的键也有自己的插入位置，RR 下加锁查询可能保护那个间隙。范围查询和普通索引的等值查询，还要沿实际使用的索引找到左右边界。看锁表时把INDEX_NAME、LOCK_MODE和LOCK_DATA合起来读，就能知道一条锁记录对应哪段范围。

总结

同一个ERROR 1205在这些实验里出现了好几次。先看在等的语句是什么，再按它访问的对象去找锁。

观察到的现象 例子里的原因 下一步看哪里
换个库还是写不了 A 持有全局读锁 找持有FLUSH TABLES WITH READ LOCK的连接，确认它有没有释放
同一张表连普通查询也卡住 A 对该表显式加了WRITE锁 看持锁连接有没有执行UNLOCK TABLES
