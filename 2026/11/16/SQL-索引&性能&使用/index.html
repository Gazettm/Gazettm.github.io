Author: Gazettm Date: 十一月 16, 2026  23:21:46 Category: SQL

SQL 索引与性能分析

索引

索引是用来加快数据查找的数据结构。比如，按工号查询一名员工时，MySQL 可以通过工号索引定位记录，减少需要检查的行数。索引会占用额外空间，插入、删除或修改索引列时，MySQL 也要维护相应的索引。

索引结构

MySQL 的索引由存储引擎实现。上一篇讲到了 InnoDB、MyISAM 和 MEMORY，它们支持的索引结构有所不同。下表以 MySQL 8.0 为例。

索引结构 说明 InnoDB MyISAM MEMORY
B+ 树索引（BTREE） 索引键有序，可以做等值查找和范围扫描 支持 支持 BTREE 支持 BTREE
哈希索引（HASH） 按索引键进行等值查找 内部有自适应哈希索引 — 支持，默认使用
空间索引（SPATIAL） 使用 R 树组织空间数据，例如地理坐标或区域 支持 支持 —
全文索引（FULLTEXT） 用倒排索引查找包含关键词的文本 支持（MySQL 5.6 起） 支持 —

InnoDB 的 B+ 树中，非叶子节点帮忙定位到正确的叶子页，叶子页按键的顺序相连。例如，查询编号在 10 到 20 之间的记录时，可以先定位到范围起点，再沿着叶子页向后扫描。MEMORY 的哈希索引适合 id = 10 这样的等值查询，范围查询需要有序的索引结构。InnoDB 的自适应哈希索引由引擎自行管理。

索引分类

分类 说明 关键字
主键索引 定义主键时自动创建，一张表只有一个主键，主键可以由多列组成 PRIMARY KEY
唯一索引 限制索引键重复，单列允许 NULL 时可以有多个 NULL UNIQUE
普通索引 用于快速定位数据，允许键值重复 INDEX
全文索引 用于在文本中搜索关键词 FULLTEXT

InnoDB 的聚集索引和二级索引

分类 叶子页保存的内容 数量
聚集索引（Clustered Index） 保存表的行记录 每张表有一个
二级索引（Secondary Index） 普通二级索引保存索引列的值和对应的聚集索引键，通常就是主键 一张表可以有多个

有主键时，InnoDB 用主键作为聚集索引。没有主键时，会选第一个所有索引列都定义为 NOT NULL 的唯一索引。如果也没有这样的唯一索引，InnoDB 会生成内部行 ID 来建立聚集索引。

例如，员工表用 id 做主键，name 上建了二级索引。假如 MySQL 选中了姓名索引来执行 SELECT * FROM employee_index_demo WHERE name = 'Arm';，查找过程可以按课件里的例子来理解。

  1. 在姓名索引里找到 Arm，读到对应的主键 10。
  2. 用主键 10 去聚集索引里找这一行，取出工号、工资等列。

第二步叫回表。如果选定的索引已经包含查询所需的列，就可以直接从索引取得这些列的值。

SQL 性能分析

查看 SQL 执行次数

SHOW GLOBAL STATUS 查看整个 MySQL 实例的状态，SHOW SESSION STATUS 查看当前连接的状态。执行次数是累计值，例如要看一分钟里执行了多少次查询，可以在间隔一分钟的两次读数之间取差值。

实测时，在同一连接中执行 SELECT id, name FROM employee_index_demo WHERE id = 10;，前后各查一次当前连接的 Com_select，计数从 3 变成了 4。

慢查询日志

慢查询日志用来找执行时间较长的 SQL。MySQL 8.0 默认关闭慢查询日志，long_query_time 默认是 10 秒。通常语句要超过这个时间阈值，并达到 min_examined_row_limit 指定的最少检查行数，才会记录。

在测试实例里把阈值设为 2 秒、min_examined_row_limit 设为 0，执行 SELECT SLEEP(2.1); 模拟一条耗时语句。慢查询日志实际记录了下面两行。

这里的 Query_time 约为 2.10 秒，超过了设置的阈值。

SHOW PROFILE 查看耗时

课件里的 SHOW PROFILES 用来查看当前连接最近执行的语句和总耗时，SHOW PROFILE 可以再展开某一条语句的各个执行阶段。MySQL 8.0 将这两条语句标为已弃用，这里按课程的写法记录。

SHOW PROFILES 中的 Duration 是语句总耗时，单位是秒。SHOW PROFILE 中的 Status 是阶段名，Duration 是该阶段的耗时。加上 CPU 后可以查看系统能提供的 CPU 时间。

本次 SHOW PROFILES 返回了下面这条记录。

Query_ID Duration Query
1 0.00006450 SELECT * FROM employee_index_demo WHERE salary = 8000

用 SHOW PROFILE FOR QUERY 1 展开，节选了几个阶段。

Status Duration（秒）
Opening tables 0.000007
optimizing 0.000003
statistics 0.000004
executing 0.000011

这次总耗时约为 65 微秒，executing 阶段约为 11 微秒。练习表只有 5 行，这些时间适合用来学怎么看输出。

EXPLAIN 执行计划

在 SELECT 前加 EXPLAIN 或 DESC，可以看优化器计划按什么顺序读表、用什么方式找记录。课件里的字段对应表格输出，下面显式用 FORMAT=TRADITIONAL 选这个格式。

三条语句的实际执行计划节选如下。

查询条件 type possible_keys key key_len rows filtered Extra
id = 10 const PRIMARY PRIMARY 4 1 100.00 NULL
salary = 8000 ALL NULL NULL NULL 5 20.00 Using where
name = 'Arm' ref idx_employee_name idx_employee_name 122 1 100.00 NULL
字段 说明
id SELECT 的编号。连接查询中的多张表可以同属一个编号，带子查询时可能出现不同编号。分析实际计划时还要结合 select_type 和表的读取顺序
select_type 查询块的类型。SIMPLE 表示没有子查询或 UNION，也可以是多表连接。PRIMARY 表示最外层查询，SUBQUERY 表示子查询中的第一个 SELECT，UNION 表示联合查询的第二个或后续 SELECT
table 当前这一行计划对应的表名或别名
partitions 可能读取的分区，普通非分区表通常为 NULL
type 访问表的方式，例如按主键查一行、扫描索引范围或全表扫描
possible_keys 优化器可能用来定位记录的候选索引
key 执行计划最终选中的索引。NULL 表示在这一步没有选用索引
key_len 计划使用的索引键长度，以字节为单位。结合列定义可以判断用到了索引键的哪些部分
ref 用于和索引键比较的常量或列，例如 const 表示常量
rows 优化器估计这一步需要检查的行数
filtered 估计有多少百分比的行通过这一表的条件过滤。比如 rows 为 100、filtered 为 20，估计有 20 行通过
Extra 补充信息，例如是否还要检查条件、排序或使用临时表

常见的 type

取值 含义
NULL 这一步可能无需访问表，例如 EXPLAIN SELECT 1;
system const 的特殊情况，优化器已知表中只有一行
const 通过主键或唯一索引与常量比较，至多匹配一行
eq_ref 做表连接时，前面每组记录在这张表里至多匹配一行，常见于按主键关联
ref 通过等值条件查索引，可能匹配多行，例如按普通姓名索引查找
range 扫描索引中的一个或多个范围
index 扫描整棵索引
ALL 全表扫描

常见的 Extra

取值 含义
Using where 还要用条件判断哪些行符合要求
Using index 查询所需的列可以从索引取得
Using filesort 需要额外做排序，排序可以在内存中完成
Using temporary 处理中使用了内部临时表

结合这次的输出，可以先看 type 和 key，再看 rows、filtered 和 Extra。

  • 按主键查。const 配合 key = PRIMARY，表示 MySQL 通过主键定位记录。这里 id 是 INT，所以 key_len 为 4 字节。
  • 按工资查。工资列上没有索引，MySQL 全表扫描，Using where 表示还要逐行用工资条件过滤。rows = 5、filtered = 20.00 表示优化器估计有 1 行通过，真正执行时返回了 Dawn 和 Lily 两行。
  • 按姓名查。ref 配合 key = idx_employee_name，表示 MySQL 用姓名二级索引做等值查找。SELECT * 还需要索引里没有的 workno 和 salary，因此要用主键回表。key_len = 122 反映的是索引键的长度，和这次查找的字符串 Arm 有几个字符是两回事。
