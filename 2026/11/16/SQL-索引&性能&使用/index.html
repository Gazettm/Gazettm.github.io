SQL 索引、性能分析与使用

索引

索引是用来加快数据查找的数据结构。比如，按工号查询一名员工时，MySQL 可以通过工号索引定位记录，减少需要检查的行数。索引会占用额外空间，插入、删除或修改索引列时，MySQL 也要维护相应的索引。

索引结构

MySQL 的索引由存储引擎实现。上一篇讲到了 InnoDB、MyISAM 和 MEMORY，它们支持的索引结构有所不同。下表以 MySQL 8.0 为例。

索引结构 说明 InnoDB MyISAM MEMORY
B+ 树索引（BTREE） 索引键有序，可以做等值查找和范围扫描 支持 支持 BTREE 支持 BTREE
哈希索引（HASH） 按索引键进行等值查找 内部有自适应哈希索引 — 支持，默认使用
空间索引（SPATIAL） 使用 R 树组织空间数据，例如地理坐标或区域 支持 支持 —
全文索引（FULLTEXT） 用倒排索引查找包含关键词的文本 支持（MySQL 5.6 起） 支持 —

InnoDB 的 B+ 树中，非叶子节点帮忙定位到正确的叶子页，叶子页按键的顺序相连。例如，查询编号在 10 到 20 之间的记录时，可以先定位到范围起点，再沿着叶子页向后扫描。MEMORY 的哈希索引适合 id = 10 这样的等值查询，范围查询需要有序的索引结构。InnoDB 的自适应哈希索引由引擎自行管理。

索引分类

分类 说明 关键字
主键索引 定义主键时自动创建，一张表只有一个主键，主键可以由多列组成 PRIMARY KEY
唯一索引 限制索引键重复，单列允许 NULL 时可以有多个 NULL UNIQUE
普通索引 用于快速定位数据，允许键值重复 INDEX
全文索引 用于在文本中搜索关键词 FULLTEXT

InnoDB 的聚集索引和二级索引

分类 叶子页保存的内容 数量
聚集索引（Clustered Index） 保存表的行记录 每张表有一个
二级索引（Secondary Index） 普通二级索引保存索引列的值和对应的聚集索引键，通常就是主键 一张表可以有多个

有主键时，InnoDB 用主键作为聚集索引。没有主键时，会选第一个所有索引列都定义为 NOT NULL 的唯一索引。如果也没有这样的唯一索引，InnoDB 会生成内部行 ID 来建立聚集索引。

例如，员工表用 id 做主键，name 上建了二级索引。假如 MySQL 选中了姓名索引来执行 SELECT * FROM employee_index_demo WHERE name = 'Arm';，查找过程可以按课件里的例子来理解。

  1. 在姓名索引里找到 Arm，读到对应的主键 10。
  2. 用主键 10 去聚集索引里找这一行，取出工号、工资等列。

第二步叫回表。如果选定的索引已经包含查询所需的列，就可以直接从索引取得这些列的值。

SQL 性能分析

查看 SQL 执行次数

SHOW GLOBAL STATUS 查看整个 MySQL 实例的状态，SHOW SESSION STATUS 查看当前连接的状态。执行次数是累计值，例如要看一分钟里执行了多少次查询，可以在间隔一分钟的两次读数之间取差值。

实测时，在同一连接中执行 SELECT id, name FROM employee_index_demo WHERE id = 10;，前后各查一次当前连接的 Com_select，计数从 3 变成了 4。

常见的 type

取值 含义

结合这次的输出，可以先看 type 和 key，再看 rows、filtered 和 Extra。

  • 按主键查。const 配合 key = PRIMARY，表示 MySQL 通过主键定位记录。这里 id 是 INT，所以 key_len 为 4 字节。
  • 按工资查。工资列上没有索引，MySQL 全表扫描，Using where 表示还要逐行用工资条件过滤。rows = 5、filtered = 20.00 表示优化器估计有 1 行通过，真正执行时返回了 Dawn 和 Lily 两行。
  • 按姓名查。ref 配合 key = idx_employee_name，表示 MySQL 用姓名二级索引做等值查找。SELECT * 还需要索引里没有的 workno 和 salary，因此要用主键回表。key_len = 122 反映的是索引键的长度，和这次查找的字符串 Arm 有几个字符是两回事。

前面介绍了怎么看 EXPLAIN。这一节用同一张用户表对照几种写法，看条件、返回列和数据分布怎样影响执行计划。

联合索引与最左前缀

idx_prof_age_status 按 profession、age、status 的顺序排列。先按职业分组，同一职业内再按年龄排列，同一职业和年龄内才按状态排列。

条件 type key key_len rows Extra
status + age + profession ref idx_prof_age_status 103 1 NULL
profession + age ref idx_prof_age_status 102 2 NULL
只有 profession ref idx_prof_age_status 98 50 NULL
profession + status ref idx_prof_age_status 98 50 Using index condition
age + status ALL NULL NULL 1000 Using where

这里的最左看的是建索引时的列顺序。第一条把 profession 写在 WHERE 最后，仍能用三个列做等值定位。第四条跳过了 age，所以只能先定位到整个职业分组；status 仍在索引里，可以先用它筛选，再对符合条件的记录回表，这就是 Using index condition 所表示的索引条件下推。第五条缺少最左列，这次选了全表扫描。

联合索引遇到范围条件

年龄条件 type key key_len rows Extra 实际返回
age > 40 range idx_prof_age_status 102 25 Using index condition 13
age >= 40 range idx_prof_age_status 103 27 Using index condition 14

age > 40 的扫描起点由职业和年龄决定；这次 age >= 40 的扫描起点还用到了 status，因此 key_len 多了 1 字节。这个变化只影响范围的边界。往后读到 age > 40 的索引项时，每个年龄下仍可能有不同的状态，仍要判断 status = 0。两条语句本来就差了年龄等于 40 的记录，写条件时以业务需要为准。

索引列上的运算、类型转换和模糊查询

条件 type possible_keys key rows
phone = '17799900015' ref idx_phone idx_phone 1
phone = 17799900015 ALL idx_phone NULL 1000
RIGHT(phone, 2) = '15' ALL NULL NULL 1000
profession LIKE 'Software%' range idx_prof_age_status idx_prof_age_status 100
profession LIKE '%Engineer' ALL NULL NULL 1000
  • 类型转换：phone 是 VARCHAR。拿它和数字比较时，MySQL 会按数值规则比较，不能用原来的字符串索引做等值定位。写 SQL 时给手机号加引号；传参数时也按字符串传。
  • 对列做运算：idx_phone 按完整手机号排序，按尾号查时无法从这个顺序找出一段连续范围。改成 phone LIKE '%15'，这次也仍然是全表扫描。按完整手机号查和按尾号查是两个不同的需求。
  • 模糊查询：LIKE 'Software%' 有固定开头，可以从索引中找到相应的范围。LIKE '%Engineer' 和 LIKE '%Engineer%' 都没有固定开头，普通 B+ 树索引无法据此缩小查找范围。

OR 条件与 UNION

先不建年龄索引。下面两条查询都要返回「编号为 60，或者年龄为 40」的用户：

查询步骤 type key rows Extra
原来的 OR ALL NULL 1000 Using where
UNION 第一支：id = 60 const PRIMARY 1 NULL
UNION 第二支：age = 40 ALL NULL 1000 Using where
UNION RESULT ALL NULL NULL Using temporary

去掉 EXPLAIN 执行后，OR 和 UNION 都返回 21 行。把 UNION 换成 UNION ALL 会返回 22 行，因为编号 60 的用户也正好是 40 岁。这里结果中包含主键 id，因此 UNION 去掉的是两支共同返回的同一个用户。如果只选 profession 之类的列，UNION 还可能把职业相同的不同用户合并掉。若想用 UNION ALL 保留原结果，这个例子可以在第二支加上 AND id <> 60，让两个分支互不重叠。

仍然只用最初的索引。在 MySQL 8.0.46 上用同一个连接预热后交替执行，每种写法计时 360 次。下表的耗时是 Performance Schema 记录的语句耗时中位数。

写法 实际返回 每次创建的临时表 中位耗时（µs）
原来的 OR 21 行 0 242.7
UNION 21 行 1 265.9
UNION ALL，第二支加 AND id <> 60 21 行 0 285.3

这批数据上保留原来的 OR 更快。UNION 仍要在第二支扫描 1,000 行，还要用临时表去重，耗时多了约 10%。排除重复的 UNION ALL 省掉了临时表，但第二支沿主键扫描了其余 999 行来筛年龄，耗时反而比原查询多约 18%。

给年龄建单列索引，再看原来的 OR：

这次 type 变为 index_merge，key 为 PRIMARY,idx_age，Extra 为 Using union(PRIMARY,idx_age); Using where。EXPLAIN ANALYZE 显示，主键索引找到 1 条，年龄索引找到 21 条，按主键合并去重后返回 21 行。同样跑 360 次，原 OR 的中位耗时从 242.7 µs 降到 83.2 µs，减少约 66%。

数据分布会影响索引选择

手机号条件 possible_keys type key rows 实际返回
>= '17799900005' idx_phone ALL NULL 1000 996
>= '17799900995' idx_phone range idx_phone 6 6

两条语句的写法一样，只换了起始值。第一条要取 996 行，走手机号索引后几乎每条都得回表，优化器选择直接扫表。第二条只需取 6 行，走手机号索引就能缩小查找范围。因此看到 possible_keys 里有索引时，还要看 key 最终选了哪个。

覆盖索引与回表

返回列与条件 type key rows Extra
返回 id, profession, age, status，按职业、年龄、状态查 ref idx_prof_age_status 1 Using index
同样的条件，多取一列 email ref idx_prof_age_status 1 NULL
SELECT *，按 id = 60 查 const PRIMARY 1 NULL

InnoDB 的二级索引叶子里还存有主键 id。第一条要的列都能从职业联合索引拿到，这条查询就被索引覆盖了。第二条用同一个索引定位，但 email 不在索引里，要拿主键回到聚集索引取完整记录。第三条直接走主键，聚集索引叶子已有整行，可以直接取出。

Using index 表示查询所需的列能从索引取得；Using index condition 表示先用索引里的值过滤，符合条件的记录还要读取整行。 第二条即使 Extra 为 NULL，也可以根据所选索引和返回列判断它要回表。业务只需要部分列时，把它们写出来更容易用上覆盖索引；本例如果通过职业二级索引执行 SELECT *，就需要回表。

前缀索引

字符串很长时，可以只给开头的一部分建索引，缩小索引占用的空间。语法是在索引列后写 列名(前缀长度)。例如，email(5) 对 VARCHAR 列保存前 5 个字符。

前缀越短越省空间，但相同前缀的记录可能越多。可以先算选择性：不同键值的个数 ÷ 总行数。下面对比完整邮箱和三种前缀长度：

单列索引、联合索引和 SQL 提示

单列索引只包含一列，联合索引包含多列。如果查询经常同时按职业、年龄和状态筛选，(profession, age, status) 可以一次用三个条件定位。但如果经常单独按年龄查，(age) 仍然有用，因为 age 在原联合索引中不是最左列。

再给 profession 单独建一个索引。这样，同一条查询既可以用单列索引，也可以用联合索引。可以把索引提示写在表名后面来做对照：

  • USE INDEX (索引名)：把可用来找行的索引限制在指定列表里，优化器仍可选择扫表。
  • IGNORE INDEX (索引名)：排除指定索引。
  • FORCE INDEX (索引名)：限制可用索引，并让优化器把全表扫描视为代价很高的选择。
写法 type key Extra
职业、年龄、状态查询，不加提示 ref idx_prof_age_status Using index
USE INDEX (idx_prof) ref idx_prof Using where
IGNORE INDEX (idx_prof) ref idx_prof_age_status Using index
对返回 996 行的手机号查询用 FORCE INDEX (idx_phone) range idx_phone Using index condition

两组查询分别在同一个连接中预热后交替执行，每种写法计时 360 次。读到的行数来自 EXPLAIN ANALYZE，中位耗时来自实际执行 SELECT 时的 Performance Schema 记录。

查询 写法 实际读取 实际返回 中位耗时（µs）
职业、年龄、状态 不加提示 联合索引 1 条，无需回表 1 62.9
职业、年龄、状态 USE INDEX (idx_prof) 职业索引命中 50 条，再回表筛选 1 88.7
职业、年龄、状态 IGNORE INDEX (idx_prof) 联合索引 1 条，无需回表 1 60.2

职业查询默认就选中了覆盖查询的联合索引，IGNORE INDEX 也得到同一个计划。用 USE INDEX 指定单列索引后，MySQL 要回表检查 50 条候选记录的年龄和状态，中位耗时增加约 41%。手机号查询要拿到几乎整张表的数据，强制走二级索引时多了 996 次按主键取整行的工作，中位耗时增加约 82%。这两组查询都保留默认计划。

索引设计原则

  1. 优先看数据量较大、访问频繁的表，从真正慢或频繁的查询入手。
  2. 考虑常用于 WHERE、ORDER BY 和 GROUP BY 的列，并结合经常一起出现的条件决定联合索引的顺序。
  3. 区分度高的列通常更容易用来缩小查找范围。性别一类的列取值少，如果两类各占一半，单独建索引往往收益有限；如果分布很不均匀，查询少数值仍可能从索引获益。只有业务需要保证值不重复时才建唯一索引。
  4. 长字符串可以比较不同前缀长度的选择性，选一个够用的长度，再看查询是否需要完整的列值。
  5. 多条件查询可以优先考虑联合索引，同时检查是否存在覆盖查询、是否还需要单独按其中某一列查询。
  6. 控制索引数量。多一个索引就多一份空间开销，增删记录或修改索引列时也多一份维护成本。对于列重复的索引，先看查询用途再决定是否保留。
  7. 业务上必填的字段用 NOT NULL 明确约束，允许缺失的字段保留 NULL。可空列也能建索引，不能仅凭是否可空判断查询会不会用它。

排查时可以按这个顺序看：先查条件能否缩小索引范围，再看优化器是否选了该索引，最后看需要的列会不会让查询回表。
