MIT6-S081-xv6-thread-switching

Author: Gazettm Date: 九月 18, 2026  21:59:56 Category: OS

前言

本文章讨论XV6实验系统如何实现线程之间的上下文切换。微观上一个单核CPU同一时刻只能运行一个线程，而宏观上却表现为并发。

设计层面

概念

我们先从设计层面来讲如何实现上下文切换。

设想我们有两个线程，其中一个为线程A，另一个为线程B。我们为了进行上下文切换，必须要保存线程A和线程B的状态之后才能切换，否则寄存器无法恢复。那么我们知道每一个线程都有一个trapframe页用于存储寄存器，那么我们能用这个吗？答案是不可以。因为这个trapframe页用于进入内核时保存寄存器状态，而且用户态的权限问题导致我们必须从内核中进行切换，因此最好的办法是使用内核统一管理，通过内核来访问内核中定义的CPU来进行上下文的切换。在xv6中，我们为每个进程定义了一个context用于在切换上下文时保存寄存器和PC寄存器等信息。（这里的context结构体定义在proc中，只有在内核中可以访问）。在线程A切换到线程B之前，我们需要保存线程A的状态到context中，然后恢复定义的cpu结构体中的context（这里 cpu 中定义结构体，是因为从进程切到调度器、再从调度器切到另一个进程，是两次独立的 swtch——调度器本身也是一条执行流，它被切走之后同样需要能“从上次的断点继续”，所以它自己的寄存器状态也要有个地方存），恢复了cpu的context之后，程序计数器此时进入调度器代码。调度器代码会循环遍历 proc 数组，找到第一个处于 RUNNABLE 的进程。跳入线程B之前，重新保存cpu的context（虽然我们的调度器代码映射在固定位置，但是我们的其他寄存器状态可能不同，比如sp栈指针不同，有时大有时小，与调度深度有关），随后进入线程B，将线程B的context恢复。

线程A保存上下文 -> cpu恢复上下文 -> 执行调度器代码 -> cpu保存上下文 -> 线程B恢复上下文（struct cpu 是 xv6 里每个物理 CPU 核心的软件状态结构体，不是物理 CPU 硬件本身。它既用于调度器，也用于记录当前核上运行的进程和中断状态）

这里我们仅仅讨论了线程B是一个旧的线程，如果线程B是一个新分配的线程，我们需要先对他进行分配，有一些细节上的不同我们到代码部分讲解。

类比下来就像是游戏中的存档一样。每次我们切换一条剧情线，需要先保存当前线A，然后返回主界面（假设不能直接加载），主界面加载上次保存的设置（比如语言，背景图），然后进行一些操作，保存这次的设置之后，进入另一条剧情线B并加载剧情线B的细节。

阶段 ra sp s0~s11 a0~a7/t0~t6
A 运行中 A 的代码地址 A 内核栈 A 的局部变量 A 的临时值
A 调用 swtch 保存 存入 A->context 存入 A->context 存入 A->context 已在 A 内核栈上
从 cpu0->context 恢复 调度器断点 调度器栈 调度器局部变量 仍是 A 的值（但调度器不用）
调度器调用 swtch 保存 存入 cpu0->context 存入 cpu0->context 存入 cpu0->context 已在调度器栈上
从 B->context 恢复 B 的断点 B 内核栈 B 的局部变量 仍是调度器的值（但 B 不用）
B 运行中 B 的代码地址 B 内核栈 B 的局部变量 B 从自己栈上重新加载

其中我们需要记得，caller和callee寄存器的区别。（context不保存a0~a7、t0~t6）

swtch 是被当作普通函数调用的（call swtch），按照 RISC-V 的调用约定，a0~a7、t0~t6 这些 caller-saved 寄存器本来就由调用者负责——如果 sched 里有需要跨切换保留的临时值，编译器会把它放到栈上或者 callee-saved 寄存器里，所以 context 只需要保存 ra、sp 和 s0~s11 这些 callee-saved 寄存器就够了。

切换时机

在xv6中，切换时机一般为

  1. 定时器中断导致进程让出 CPU
  2. sleep函数的调用
  3. 从磁盘中读取数据
  4. 等待管道的输入输出
  5. exit进程退出
  6. wait等待子进程

其中，等待子进程，磁盘I/O，管道的等待都是通过sleep函数来实现。

这里的mycpu()->noff != 1是什么？noff指的是当前 CPU 上，中断被关了多少层。

如果为0，表明中断没有关闭，那么可能在执行过程中被中断，导致调度器的状态混乱，锁也会变得混乱。

如果大于1，说明当前有嵌套的情况，外层嵌套可能未释放一个锁，同样会导致错误。

intena同样与中断有关，指的是interrupt enable ，用于开关中断。（sched函数调用前可能处于关中断状态，这里需要保存，之后swtch之后再进行恢复。）

然后是调用swtch函数。

swtch 必须用汇编来写。因为它要做的事情是“精确地保存和恢复每一个寄存器”，而 C 编译器在编译函数时会自作主张地使用这些寄存器（比如把某个变量放进 s0），这样就没办法保证“保存下来的就是调用之前的状态”了。这类直接操作机器的代码只能用汇编来控制。

这里的 swtch 函数很简单：在两个 context 结构体之间，一个保存、一个加载。这时，A的ra寄存器被保存到

而调度器的ra寄存器被加载进来指向的是scheduler函数。

此时，调度器开始查找进程，如果哪个进程RUNNABLE，那么就改为RUNNING，再进行切换。

此时寄存器又被更新为B之前的上下文，跳转到swtch函数，在函数中return，跳转到B之前的进程。此时有一处细节：如果线程B是新创建的，那么将跳转到forkret函数。

forkret 里做了几件收尾的事情：释放 p->lock（新进程在 allocproc 之后一直持有它）、初始化文件系统（只有第一个进程需要），最后调用 usertrapret() 回到用户态——这就是一个新进程第一次进入用户态的路径。
